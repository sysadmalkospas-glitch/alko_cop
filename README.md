# AlkoCop

Своя система учёта рабочего времени и активности сотрудников за компьютером
для сети из трёх клиник. Аналог Bitcop, работающий на локальном сервере.

План реализации и выбранные возможности ведутся в отдельных документах проекта.
Задачи — в GitHub issues (сводка в #1), правила работы с ними — в `AGENTS.md`.
Сейчас в репозитории **каркас этапа 1**: приём данных на сервере и сбор
активности агентом.

## Как устроено

```
 ПК сотрудника (Windows 10/11)                 Сервер в офисе
┌──────────────────────────────────┐          ┌───────────────────────────┐
│ Служба AlkoCopAgent (SYSTEM)     │  HTTPS   │ FastAPI (server/)         │
│  • очередь SQLite                ├─────────►│  • /api/agent/v1/...      │
│  • регистрация, отправка         │  по VPN  │ PostgreSQL                │
│  • события входа/выхода/блок.    │          │ Скриншоты на диске        │
│  • запуск сборщика в сессиях     │          └───────────────────────────┘
│        ▲ именованный канал       │
│ AlkoCopCollector (в сессии       │
│ пользователя, в т.ч. RDP)        │
│  • активное окно, процесс        │
│  • простой по клавиатуре и мыши  │
└──────────────────────────────────┘
```

* **Служба** работает от SYSTEM, хранит токен доступа и очередь отправки.
  Пока сервер или VPN недоступны, данные копятся в очереди и уходят позже.
* **Сборщик** запускается службой в каждой активной сессии и каждую секунду
  снимает активное окно и время без ввода. Простой засчитывается задним
  числом с момента последнего ввода. На сервер сборщик сам не ходит.
* Логин и номер сессии служба определяет по подключившемуся процессу,
  поэтому пользователь не может отправить данные от чужого имени.
* **Сервер** принимает отрезки активности, системные события и скриншоты.
  Повторная отправка той же записи не создаёт дублей.

## Структура

| Каталог | Что внутри |
|---|---|
| `server/` | Сервер на Python (FastAPI, SQLAlchemy, PostgreSQL) и тесты |
| `agent/src/AlkoCop.Agent.Core` | Общая логика агента: отрезки активности, очередь, клиент API |
| `agent/src/AlkoCop.Agent.Service` | Служба Windows |
| `agent/src/AlkoCop.Agent.Collector` | Сборщик в сессии пользователя |
| `agent/tests` | Тесты логики агента |
| `agent/install` | Скрипт установки агента |
| `deploy/` | Docker Compose для сервера |

## Сервер

Запуск через Docker Compose (Linux, или Linux-машина в Hyper-V на Windows):

```bash
cd deploy
cp .env.example .env   # задать пароли и ключ регистрации агентов
docker compose up -d --build
curl http://localhost:8000/health
```

Документация API: `http://<сервер>:8000/docs`.

Разработка и тесты:

```bash
cd server
python -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Настройки берутся из переменных окружения `ALKOCOP_*` (см. `server/app/config.py`).
Схема БД управляется Alembic: контейнер автоматически выполняет
`alembic upgrade head` перед запуском FastAPI. Если миграция завершается
ошибкой, сервер не запускается.

### Миграции базы данных

Команды для разработки выполняются из каталога `server/` в активном
виртуальном окружении. Укажите `ALKOCOP_DATABASE_URL` для нужной тестовой БД
(или настройте `.env` согласно `app/config.py`).

```bash
alembic upgrade head
alembic check
```

После изменения моделей создайте миграцию, проверьте её код и примените:

```bash
alembic revision --autogenerate -m "describe schema change"
alembic upgrade head
alembic check
```

Новая БД создаётся первой миграцией `0001`. Если БД была создана ранним
каркасом через `create_all`, сначала сделайте резервную копию и убедитесь,
что её схема полностью соответствует миграции `0001`. Только после этого
можно отметить начальную ревизию без повторного создания таблиц:
`alembic stamp 0001`, затем `alembic upgrade head` и `alembic check`. При несовпадении схемы не
продолжайте обновление до проверки и устранения расхождений.

В Docker Compose команду для уже запущенного сервера можно выполнить через
`docker compose exec server alembic check`. Для разового обслуживания
до запуска сервера с существующей БД используйте
`docker compose run --rm --entrypoint alembic server <команда>` из `deploy/`.

### Вход в веб-кабинет

После первого запуска создайте администратора из каталога `deploy/`:

```bash
docker compose exec server python -m app.cli create-admin
```

При запуске сервера без Docker выполните `python -m app.cli create-admin`
из `server/` с настроенным подключением к БД. Команда запросит логин,
пароль (12–1024 символа) и его подтверждение без отображения пароля.
Если пользователь кабинета уже существует, команда не создаст ещё одного.
Пароли по умолчанию отсутствуют.

API кабинета:

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/auth/login` | Вход: JSON с полями `login` и `password` |
| GET | `/api/v1/auth/me` | Данные текущего пользователя |
| POST | `/api/v1/auth/logout` | Выход с отзывом сессии на сервере |

Вход создаёт серверную сессию на 12 часов. Cookie имеет атрибуты
`HttpOnly`, `Secure` и `SameSite=Strict`. Пароли хранятся как хеши Argon2id,
а токены сессий — только как хеши. После пяти неудачных попыток входа
для одного логина или 30 попыток с одного IP вход ограничивается в
15-минутном окне (HTTP 429). API агента использует собственную авторизацию,
не связанную с кабинетной сессией.

**Для рабочей эксплуатации нужен HTTPS** (см. T03). Reverse proxy должен
передавать исходное имя хоста и схему HTTPS через доверенные прокси-заголовки;
настройте доверие только к адресу своего прокси. Веб-кабинет и его API должны
работать с одного origin. Тестировать через обычный HTTP допускается только
на локальной машине: явно установите `ALKOCOP_AUTH_COOKIE_SECURE=false` в
`deploy/.env` (или переменной окружения сервера без Docker), затем пересоздайте
контейнер. На рабочем сервере оставьте `true`.

Для новых API кабинета используйте зависимость `app.auth.current_user`
(или тип `app.auth.CurrentUser`); без действующей сессии запрос отклоняется.

## Агент

Нужен .NET SDK 10.

```bash
cd agent
dotnet test AlkoCop.Agent.slnx
dotnet publish src/AlkoCop.Agent.Service   -c Release -r win-x64 --self-contained -o publish
dotnet publish src/AlkoCop.Agent.Collector -c Release -r win-x64 --self-contained -o publish
```

Установка на ПК сотрудника (PowerShell от администратора):

```powershell
.\install-agent.ps1 -ServerUrl https://<сервер>:8000/ -EnrollKey <ключ> -SourceDir .\publish
```

Скрипт ставит службу с автозапуском и перезапуском при сбое и закрывает
файлы агента от обычных пользователей.

## Что уже есть и чего пока нет

Есть: регистрация агента, настройки мониторинга с сервера (включая качество,
формат и разрешение скриншотов), отрезки активности с простоем, события входа,
выхода, блокировки и старта агента, приём скриншотов на сервере, работа в RDP.

Следующие шаги этапа 1–2: снимки экрана в агенте, адреса сайтов и поисковые
запросы, веб-кабинет с отчётами, сотрудники и офисы в интерфейсе.

Известные ограничения каркаса:

* Агент проверен сборкой и тестами логики, но ещё не запускался на реальной
  Windows: это первый шаг пилота.
* Пользователь может завершить процесс сборщика в диспетчере задач; служба
  перезапустит его в течение 10 секунд. Более сильная защита — этап 3.
