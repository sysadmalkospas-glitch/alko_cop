# AlkoCop

Своя система учёта рабочего времени и активности сотрудников за компьютером
для сети из трёх клиник. Аналог Bitcop, работающий на локальном сервере.

План реализации и выбранные возможности ведутся в отдельных документах проекта.
Задачи — в GitHub issues (сводка в #1), правила работы с ними — в `AGENTS.md`.
Сейчас в репозитории **каркас этапа 1**: приём данных на сервере и сбор
активности агентом.

## Как устроено

```
 ПК сотрудника (Windows 10/11)                 Сервер в офисе
┌──────────────────────────────────┐          ┌───────────────────────────┐
│ Служба AlkoCopAgent (SYSTEM)     │  HTTPS   │ FastAPI (server/)         │
│  • очередь SQLite                ├─────────►│  • /api/agent/v1/...      │
│  • регистрация, отправка         │  по VPN  │ PostgreSQL                │
│  • события входа/выхода/блок.    │          │ Скриншоты на диске        │
│  • запуск сборщика в сессиях     │          └───────────────────────────┘
│        ▲ именованный канал       │
│ AlkoCopCollector (в сессии       │
│ пользователя, в т.ч. RDP)        │
│  • активное окно, процесс        │
│  • простой по клавиатуре и мыши  │
└──────────────────────────────────┘
```

* **Служба** работает от SYSTEM, хранит токен доступа и очередь отправки.
  Пока сервер или VPN недоступны, данные копятся в очереди и уходят позже.
* **Сборщик** запускается службой в каждой активной сессии и каждую секунду
  снимает активное окно и время без ввода. Простой засчитывается задним
  числом с момента последнего ввода. На сервер сборщик сам не ходит.
* Логин и номер сессии служба определяет по подключившемуся процессу,
  поэтому пользователь не может отправить данные от чужого имени.
* **Сервер** принимает отрезки активности, системные события и скриншоты.
  Повторная отправка той же записи не создаёт дублей.

## Структура

| Каталог | Что внутри |
|---|---|
| `server/` | Сервер на Python (FastAPI, SQLAlchemy, PostgreSQL) и тесты |
| `web/` | Веб-кабинет на React и TypeScript |
| `agent/src/AlkoCop.Agent.Core` | Общая логика агента: отрезки активности, очередь, клиент API |
| `agent/src/AlkoCop.Agent.Service` | Служба Windows |
| `agent/src/AlkoCop.Agent.Collector` | Сборщик в сессии пользователя |
| `agent/tests` | Тесты логики агента |
| `agent/install` | Скрипт установки агента |
| `deploy/` | Docker Compose для сервера |

## Сервер

Запуск через Docker Compose (Linux, или Linux-машина в Hyper-V на Windows):

```bash
cd deploy
cp .env.example .env   # задать пароли, ключ регистрации и имя HTTPS-сервера
docker compose up -d --build
```

### HTTPS и доверие к сертификатам

В `deploy/.env` задайте `ALKOCOP_HOST` (например, `alkocop.internal`)
и обеспечьте разрешение этого имени в IP сервера через локальный DNS.
Имя (или IP) должно быть без схемы и порта и совпадать с сертификатом.
Порт HTTPS по умолчанию — 443 (`ALKOCOP_HTTPS_PORT`).
Наружу публикуется только HTTPS-порт Caddy; HTTP-порты FastAPI (8000)
и PostgreSQL (5432) не публикуются. Старый параметр `SERVER_PORT` больше
не используется.

**Режим 1 — внутренний CA Caddy (по умолчанию, `ALKOCOP_TLS_MODE=internal`).**
После запуска выгрузите корневой сертификат на сервере:

```bash
docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt ./alkocop-root.crt
sha256sum ./alkocop-root.crt
curl --cacert ./alkocop-root.crt https://alkocop.internal/health
```

Подставьте фактическое имя и порт. Ожидаемый ответ: `{"status":"ok"}`.
Документация API: `https://alkocop.internal/docs`.
Тома `caddy-data` и `caddy-config` сохраняют CA и настройки при пересоздании
контейнера. Защищайте и резервируйте их; не удаляйте тома через
`docker compose down -v` на рабочем сервере.

Передайте только публичный файл `alkocop-root.crt` администраторам ПК
доверенным способом; сверяйте SHA-256 файла по отдельному доверенному каналу.
Не передавайте приватные ключи CA. На Windows установите сертификат
в хранилище доверенных корневых центров компьютера (а не только пользователя),
чтобы ему доверяла и служба агента от SYSTEM:

```powershell
Get-FileHash .\alkocop-root.crt -Algorithm SHA256
certutil -addstore Root .\alkocop-root.crt
```

Выполняйте импорт от администратора только после сверки отпечатка.
При наличии домена используйте GPO: Конфигурация компьютера → Политики →
Конфигурация Windows → Параметры безопасности → Политики открытого ключа →
Доверенные корневые центры сертификации → Импорт. Примените политику только
к управляемым ПК; см. [инструкцию Microsoft](https://learn.microsoft.com/en-us/windows-server/identity/ad-cs/distribute-certificates-group-policy).
Проверьте открытие HTTPS-адреса в браузере без предупреждений
и доступ агента. Если браузер использует отдельное хранилище доверия,
настройте его по корпоративной политике. Не отключайте проверку сертификата.

**Режим 2 — готовый сертификат (`ALKOCOP_TLS_MODE=custom`).**
Поместите в каталог `ALKOCOP_CERTS_DIR` (по умолчанию `deploy/certs/`)
сертификат с цепочкой промежуточных сертификатов в PEM `tls.crt` и
соответствующий приватный ключ в PEM `tls.key`. Доступ к ключу ограничьте
администратором и контейнером Caddy; не добавляйте его в Git.
Задайте `ALKOCOP_TLS_MODE=custom` в `.env`, перезапустите Caddy:

```bash
docker compose up -d --force-recreate caddy
```

Для собственного CA установите его публичный корневой сертификат на ПК
аналогичным образом. Для сертификата от уже доверенного CA дополнительный
импорт не требуется. Проверьте `https://<имя>/health` с проверкой сертификата.
Режим `custom` не запрашивает сертификаты автоматически; при обновлении
файлов пересоздайте Caddy.

**Сеть и proxy-заголовки.** Caddy и FastAPI общаются по отдельной сети
`proxy_net`, PostgreSQL доступен только в `db_net`.
Uvicorn доверяет `X-Forwarded-Proto` и `X-Forwarded-For` только адресу
Caddy (`ALKOCOP_PROXY_IP`), поэтому HTTPS-вход и ограничение попыток входа
по клиентскому IP работают через прокси. Не задавайте доверие ко всем адресам.
Если подсеть пересекается с существующей сетью Docker или VPN, в `.env`
измените `ALKOCOP_PROXY_SUBNET`, `ALKOCOP_PROXY_DYNAMIC_RANGE` и
`ALKOCOP_PROXY_IP` до запуска. Фиксированный IP Caddy должен находиться
в общей подсети, но вне диапазона динамической выдачи Docker.

Разработка и тесты:

```bash
cd server
python -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest -q
```

Настройки берутся из переменных окружения `ALKOCOP_*` (см. `server/app/config.py`).
Схема БД управляется Alembic: контейнер автоматически выполняет
`alembic upgrade head` перед запуском FastAPI. Если миграция завершается
ошибкой, сервер не запускается.

### Миграции базы данных

Команды для разработки выполняются из каталога `server/` в активном
виртуальном окружении. Укажите `ALKOCOP_DATABASE_URL` для нужной тестовой БД
(или настройте `.env` согласно `app/config.py`).

```bash
alembic upgrade head
alembic check
```

После изменения моделей создайте миграцию, проверьте её код и примените:

```bash
alembic revision --autogenerate -m "describe schema change"
alembic upgrade head
alembic check
```

Новая БД создаётся первой миграцией `0001`. Если БД была создана ранним
каркасом через `create_all`, сначала сделайте резервную копию и убедитесь,
что её схема полностью соответствует миграции `0001`. Только после этого
можно отметить начальную ревизию без повторного создания таблиц:
`alembic stamp 0001`, затем `alembic upgrade head` и `alembic check`. При несовпадении схемы не
продолжайте обновление до проверки и устранения расхождений.

В Docker Compose команду для уже запущенного сервера можно выполнить через
`docker compose exec server alembic check`. Для разового обслуживания
до запуска сервера с существующей БД используйте
`docker compose run --rm --entrypoint alembic server <команда>` из `deploy/`.

### Вход в веб-кабинет

После первого запуска создайте администратора из каталога `deploy/`:

```bash
docker compose exec server python -m app.cli create-admin
```

При запуске сервера без Docker выполните `python -m app.cli create-admin`
из `server/` с настроенным подключением к БД. Команда запросит логин,
пароль (12–1024 символа) и его подтверждение без отображения пароля.
Если пользователь кабинета уже существует, команда не создаст ещё одного.
Пароли по умолчанию отсутствуют. Откройте главную страницу сервера по HTTPS
и войдите под созданным пользователем.

API кабинета:

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/auth/login` | Вход: JSON с полями `login` и `password` |
| GET | `/api/v1/auth/me` | Данные текущего пользователя |
| POST | `/api/v1/auth/logout` | Выход с отзывом сессии на сервере |

Вход создаёт серверную сессию на 12 часов. Cookie имеет атрибуты
`HttpOnly`, `Secure` и `SameSite=Strict`. Пароли хранятся как хеши Argon2id,
а токены сессий — только как хеши. После пяти неудачных попыток входа
для одного логина или 30 попыток с одного IP вход ограничивается в
15-минутном окне (HTTP 429). API агента использует собственную авторизацию,
не связанную с кабинетной сессией.

В Docker Compose HTTPS и защищённые cookie включены всегда. Веб-кабинет
и его API должны работать с одного origin. При разработке без Docker
тестирование через HTTP допускается только на локальной машине:
установите `ALKOCOP_AUTH_COOKIE_SECURE=false` в окружении локального
FastAPI. На рабочем сервере не отключайте эту проверку.

Для новых API кабинета используйте зависимость `app.auth.current_user`
(или тип `app.auth.CurrentUser`); без действующей сессии запрос отклоняется.

### Разработка веб-кабинета

Нужен Node.js 24. Запустите локальный FastAPI на порту 8000 с
`ALKOCOP_AUTH_COOKIE_SECURE=false`. Vite проксирует API на этот сервер,
чтобы браузер обращался к кабинету и API с одного адреса.

```bash
cd web
npm ci
npm run dev
```

Проверки кабинета: `npm run lint`, `npm run typecheck`, `npm test`,
`npm run build`. При развёртывании Docker Compose собирает кабинет
в статические файлы и раздаёт их через Caddy.

## Агент

Для разработки нужен .NET SDK 10:

```bash
cd agent
dotnet test AlkoCop.Agent.slnx
dotnet publish src/AlkoCop.Agent.Service   -c Release -r win-x64 --self-contained -o publish
dotnet publish src/AlkoCop.Agent.Collector -c Release -r win-x64 --self-contained -o publish
```

Релизы Windows-агента собираются в GitHub Actions по тегам вида
`agent-v1.2.3` или `agent-v1.2.3-rc.1`. После сборки и проверки ZIP
`alkocop-agent-win-x64.zip` появляется в соответствующем GitHub Release.
Версия из тега передаётся на сервер при регистрации агента.

Для установки распакуйте весь ZIP на ПК с Windows x64. Устанавливать .NET
на этот ПК не нужно. Из распакованного каталога запустите PowerShell от
администратора:

```powershell
.\install-agent.ps1 -ServerUrl 'https://alkocop.internal/' -EnrollKey '<ключ>'
```

Скрипт устанавливает службу с автозапуском и перезапуском при сбое.
Доступ к ключу регистрации и локальным данным остаётся у SYSTEM и
администраторов. При ручной сборке используйте скрипт из `agent/install`
и передайте путь к каталогу `publish` через `-SourceDir`.

Для удаления из распакованного каталога запустите от администратора:

```powershell
.\uninstall-agent.ps1
```

Скрипт удаляет службу и файлы программы. Очередь и данные регистрации
сохраняются для повторной установки. Если их тоже нужно удалить, добавьте
`-RemoveData`. Если программа уже удалена, а данные хранились в другом
каталоге, укажите его через `-DataDir`.

### Скриншоты в Windows-агенте

После получения профиля с сервера сборщик снимает каждый монитор активной
пользовательской сессии по интервалу и при смене программы. Захват приостанавливается
на экране блокировки и в отключённых RDP-сессиях. Профиль задаёт параметры
JPEG, WebP или AVIF, качество, максимальную ширину и пропуск почти одинаковых кадров.
Агент применяет обновлённый профиль в работающей сессии.

Служба отправляет кадры на настроенный сервер AlkoCop и хранит очередь в
`pending-screenshots` внутри каталога данных агента. Лимит очереди составляет
2 ГиБ. При заполнении удаляются самые старые кадры, а очередь активности
хранится отдельно. Ограничение размера одного кадра составляет 5 МиБ.

## Что уже есть и чего пока нет

Есть: регистрация агента, настройки мониторинга с сервера (включая качество,
формат и разрешение скриншотов), отрезки активности с простоем, события входа,
выхода, блокировки и старта агента, сбор и приём скриншотов, работа в RDP.

Следующие шаги этапа 1–2: адреса сайтов и поисковые запросы, веб-кабинет с
отчётами, сотрудники и офисы в интерфейсе.

Известные ограничения каркаса:

* Агент проверен сборкой и тестами логики, но ещё не запускался на реальной
  Windows: это первый шаг пилота.
* Пользователь может завершить процесс сборщика в диспетчере задач; служба
  перезапустит его в течение 10 секунд. Более сильная защита — этап 3.
